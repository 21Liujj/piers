# Cursor efficiency handoff

Repository: https://github.com/21Liujj/piers

你接手的是 PIERS 室外全景分割项目的效率优化。请先阅读仓库 REPRODUCE.md、docs/piers/PAPER_RELEASE_STATUS_20261109.md、results/paper20261109/，核验当前代码、进程和数据，再修改。附件和仓库旧文档是参考资料；本提示词给出的用户目标优先。

一、用户的验收目标

保留 I1/I2/I3 和真实开放词汇指定分割能力：推理输入只有图片、几何和用户指定类别，不限 DensePASS13类。完整模型在同一设备、相同图片/分辨率/查询集合、相同计时范围下，整体端到端耗时要低于原始 OmniSAM，分割指标同时提升。不能用“Memory模块更快”或“token变成1/32”替代系统收益。当前目标尚未实现；不要预先承诺一定能够实现。

先处理效率，不做室内适配、目标域LoRA微调或UDA。先冻结当前完整v3作为对照，优化另建配置/分支；保留失败结果。只要改了输出、类别提示或计算窗口，就要重测精度；不能沿用原分数。

三、模型和Memory的真实情况

I1：推理期DINO+文本SAM2+源域校准的文本/语义协同；与checkpoint中没有训练张量的内置CLIP text_fusion不是同一个东西。
I2：uncertainty-ranked class-aware稀疏Memory Attention输入选择；当前keep_ratio=.03125，最多32768->1024个token。密集历史特征仍然驻留，没有真正压缩整个MemoryBank。早期开题2048是另一个历史预算；默认1024来自11月6日冻结配置。历史18行选择矩阵未完整找回，不要编造其重验结果。
I3：18个原始正反向窗口之外，增加2个自适应接缝窗口，共20次语义forward。
开放词汇：v2修复了相关FoV证据重复计数和Ground/Other/Static/Moving宽泛类的覆盖；v3保留vehicles/pedestrian原词查询并保留car/person规范词，别退回会丢类别的老版本。Syn22早期完整模型18.0593是失败版本，v3才是25.6163。

四、当前效率证据：必须如实保留

RTX6000D真实端到端（3图x2重复/任务，预热后，排除模型初次加载）：
Wild8：原始4.20s/张，完整16.09s/张。
Syn22：原始4.36s/张，完整19.47s/张。
Syn13：原始4.07s/张，完整12.51s/张。
设备使用峰值约原始6.31GiB、完整9.30GiB。并行准确率任务的吞吐不能作为单请求延迟。

严格控制同底座/输入/窗口的I2-only局部实验：Memory Attention区间约332.25->79.87ms（-75.96%），固定CPU亲和性ABBA语义分支4.512->4.290s（约-4.92%）。整段峰值分配几乎不变，原始dense历史仍驻留；窗口合并临时张量是大峰值来源。

更关键的完整功能I2开关消融：I1/I3/真实DINO/SAM2全部相同，只开关I2。Dense100无I2 60.92178301，有I2 60.85548850，差-0.06629451pp，区间[-0.5544,+0.3502]；不能称统计等价证明。端到端ABBA平均13.45694->13.38210s，仅约-0.556%，中位数13.51492->13.50833s基本相同；设备峰值9456.375->9522.4375MiB。不能再说“没有I2整套一定明显更慢、显存更多”。

Jetson目前可核查的阶段性结果是相同图片/顺序的前63次预热后请求（不是已完成300次）：原始e2e4.29759s，完整67.16242s；原始语义4.13498s，完整语义core4.47061s、fusion2.76474s；文本59.52166s约占88.6%；Memory区间1044.07->707.89ms。不能把桌面GPU数字换算成Jetson。核查其他正在运行的正式Jetson任务，勿中断或把旧结果说成实时进度。

Jetson已启用降低窗口合并峰值的实现（reference_merge:false），不是仍然用1GiB窗口缓冲旧实现；不要重复宣称首次修复。另一个部署工作已记录当前全景内SAM缓存4裁剪，以及语义encoder缓存11条约160MiB；请先核对实际运行源码，避免重复做已有缓存。配置encoder_engine:null，虽有旧TensorRT encoder engine文件，但不能把“文件存在”说成正式运行使用了TensorRT。当前Jetson配置是FP16 PyTorch，没有已证明的完整TensorRT加速。

五、已经实现的第一项候选优化

src/piers_ljj/text/feature_cache.py：GroundingDINO融合前特征缓存；视觉backbone和投影按同一FoV复用，独立BERT文本backbone按原始规范化查询复用，文本LRU上限128。多模态encoder/decoder仍每条原查询重新计算。不要跨不同文本复用融合后的encoder_outputs。HF会追加position_embeddings列表，缓存返回时必须复制容器，防止列表被反复污染。eval/no_grad才启用；改变权重、dtype、device后要invalidate。

GroundedConfig.cache_prefusion_features默认False。矩阵full_cached是候选；冻结主模型full保持关闭。src/piers_ljj/workers/entry.py已接入。三个有针对性的缓存单测通过，开放词汇/查询契约等合计24个相关测试通过。

RTX6000D三个固定图片、每图2次计时的真实文本分支：Dense13 6.56856->4.55885s(-30.60%)；Wild8 9.07649->6.11990s(-32.57%)；Syn22 12.81811->8.25254s(-35.62%)。所有抽测框、分数、SAM质量、类别词、打包mask字节完全一致。缓存版设备峰值略升3611->3649MiB，不能称降低总显存。原始记录results/paper20261109/text_cache_candidate.json。它尚未完成全量精度/端到端及Jetson验证，不能说效率目标达成。

六、建议的工作顺序

1. 核查当前原始/完整运行配置、计时范围、实际调用次数和各阶段耗时。完成缓存候选的完整端到端ABBA配对与预测核对；不要用已落盘检测框或mask代替真推理测速。确认处理新图、新类别、重复类别时的缓存口径和冷/热启动开销。
2. 文本占绝大部分时间，单纯I2无法解决。研究合并多类别提示、批量类别/框处理、减少重复图像编码和跨进程搬运。多类别同一提示会改变预测，不能当作严格等价优化。保留所有请求类别，对类别短语/token关联做严格校验。减少FoV/窗口、降低分辨率或替换模型均须注册为新方法并完整验证精度。
3. 同时优化语义核心：审计正反向重复编码是否已缓存、矩阵合并/CPU往返、I3窗口与融合成本，评估FP16/TensorRT等在真实设备上的收益。通用引擎优化也应给原始基线同样机会，另外报告优化后的公平基线；不能只给完整模型更强硬件/精度后端来宣称算法更快。
4. 真正的Memory存储压缩需要改变写入/保存的数据，而非只在读出时索引。若做，验证位置编码、历史伪标签、类别配额、接缝恢复和模型精度，并分别量测常驻内存、临时峰值和延迟。不要只凭token比例推导。
5. 先用源域/开发数据确定策略和阈值；不要反复利用Wild/Syn评测GT挑参数再叫zero-shot。速度方案稳定后，再重跑三套数据上的四个口径、精度和效率。每个候选记录模型/源码hash、依赖、硬件、种子、预热、每次请求原始时间、功耗、温度、峰值内存。

七、最终交付/通过标准

必须交付可执行代码、冻结配置、原始逐请求记录、精度混淆矩阵和配对表。至少包含原始OmniSAM、当前完整v3、优化后完整模型；必要时加同样优化后端的原始基线。
速度：同设备/功耗/输入/指定类别/计时范围，完整模型真实e2e低于公平原始基线，有足够预热和重复，报告均值/中位数/P95、加载时间、吞吐、GPU/系统峰值内存和能耗；不能将阶段计时、并发吞吐、跨图结果缓存混成单图e2e。
精度：优化版本重新跑完整测试，报告mIoU及各类IoU、mAcc/PixelAcc/FWIoU/mDice与配对变化；相对原始基线有提升，且保留开放词汇新类别输出。轻微变化也不能直接沿用旧表。
若无法同时达到速度/精度目标，明确报告最好的实测折中和未达标项，不编造完成，不把功能增加直接当成“高效”。最终把可复现方案和结果提交仓库，更新REPRODUCE和状态页，确保新服务器可clone后按说明运行。
